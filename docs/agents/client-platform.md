# Mobile and browser behavior

## Mobile software keyboard (`hooks/useViewportHeight.ts`)
- While an editor has focus and the visual viewport is more than `KEYBOARD_MIN_HEIGHT_PX` (60px) shorter than `innerHeight / scale`, the hook writes `visualViewport.height` to `--app-viewport-height`; smaller shrinks are Safari toolbars. Always compare against that zoom-corrected height, or iOS auto-zoom and pinch zoom leave the composer behind the keyboard.
- WebKit settles the shrunken height only after the keyboard animation, often without another `resize` (bugs.webkit.org 265578), and an IME candidate bar resizes the keyboard with no viewport event at all. So every trigger, composition/input/keyup events on a focused editor included, starts one non-restarting chain of re-reads (`SETTLE_DELAYS_MS`). Reading once per event keeps the full-screen height, and `scrollTo(0, 0)` then fights the page scrolling to the caret: a jittering composer.
- The same check sets `<html data-keyboard-open>`. Under `(max-width: 640px), (pointer: coarse) and (max-height: 500px)` (phone landscape included; tablets keep their controls) CSS hides `.chat-input-controls`, `.extension-status-shelf` (the extension widgets' strip — the statuses read in the header's Session stats card, sessions.md) and a fresh composer's project bar (`.new-session-context`, its own rule: tapping it would close the keyboard anyway) and drops the bottom safe-area padding the keyboard covers. `MobilePwaLayout.test.mjs` asserts each targeted class exists on its component, so a rename cannot leave a rule silently dead.
- `.chat-input-controls` stays while its model picker is open (`:not(:has(...))`, a rule of its own): the picker's panel lives in that row and its filter is the field the keyboard opened for, so hiding the row hid the picker and blurred the filter (#1271). See [models.md](models.md#model-selector-and-the-mobile-keyboard).
- Anything fixed to the bottom of a phone screen sits inside `--app-viewport-height`, never at `bottom: 0`: iOS keeps the layout viewport, and with it `bottom: 0`, under the keyboard. The drawer and the right panel use `top: 0` with that height; the sidebar's bottom sheet (`.sidebar-sheet-layer` in `app/sidebar-menu.css`) is a layer of that height with the sheet at its bottom, and drops its safe-area padding under `html[data-keyboard-open]`.
- The composer's queued steer/follow-up rows scroll in their own box, `min(180px, 25%)` of `--app-viewport-height` (plain `dvh` misses a keyboard that shrinks only the visual viewport), with the count and Recall above it (#1428). The composer sits outside the scrolling transcript, so an unbounded list pushed the input and its buttons below the screen with no way to scroll them back. The composer's wrapper, fieldset and inner column are flex columns that may shrink (`min-height: 0`), so in a window too short even for that cap the queue box gives way down to its header and one row (`minHeight: 72`) before the input and buttons leave the screen; the 200px draft cap is unchanged.

## Installed web app (`hooks/useStandaloneSafeArea.ts`, native-theme.css)
- In a browser tab the shell's inline `env(safe-area-inset-*)` padding is the whole inset story, which is why the same build reads correctly in mobile Safari. In an iPhone's home-screen app WebKit draws the status bar over the page and reports the top inset as 0, and the fork's `.app-topbar { height: 48px !important }` overrides AppShell's inline `calc(36px + env(safe-area-inset-top))`: the bar became one 48px row at the window's top edge, the notch sat on its title, the file tabs behind it, and the fixed panel toggle (`top: 10px`) and the notice shelf sat under the same strip.
- So the shell's inset hangs on `<html data-standalone-safe-area>`, set by `useStandaloneSafeArea()` for a standalone display on a machine with `navigator.maxTouchPoints > 0`. A floor is needed (59px, the floor settings.css already uses for the settings dialog's top padding), and a floor must not reach a desktop browser or the Tauri window, where 0 is the honest value — the touch check is what separates them. `env()` wins over the floor wherever it is real, so a landscape notch and a taller future device are respected.
- The rules pad boxes, not heights: `.app-topbar` grows by the inset (box-sizing is border-box app-wide, so padding alone would spend its 48px and spill the title into the chat), the sidebar and the right panel get `padding-top` (both are fixed overlays on a phone, so the shell's padding never reaches them), and `.app-shell` takes a 20px floor for the home indicator. `html[data-keyboard-open]` stays the last word on the terminal's extra-keys row, whose keyboard rule has the same specificity.
- Every `env(safe-area-inset-*)` is 0 without `viewport-fit=cover`, so the installed app needs it on its own viewport source. Safari reads that only from the page's meta tag (`app/layout.tsx`'s `viewportFit: "cover"`) — no Safari version supports the manifest's `viewport` member — and Chromium 124+ reads it from the manifest for an installed app. `/manifest.webmanifest` carries `width=device-width, initial-scale=1, viewport-fit=cover` as well; the two sources must stay identical, because a manifest without it silently zeroes the insets of an installed Chromium app.
- The two fixed overlays take the bottom inset as well as the top one. On a phone `.sidebar-container` is `top: 0; bottom: 0` and `.right-panel-container` is `inset: 0 env(right) 0 env(left)`, both at `height: var(--app-viewport-height, 100dvh)`, so they end at the window's bottom edge where the shell's padding cannot reach them, and their inline `paddingBottom: env(safe-area-inset-bottom)` is 0 in the installed app: the sidebar's settings row, the file tree's last row, a terminal's body and the calendar sheet all sit on the home indicator. `.terminal-extra-keys` pads by `env()` and is 0 there for the same reason.
- Chromium cannot emulate `display-mode: standalone`, so `e2e`-style checks drive the hook through fullscreen (`(display-mode: fullscreen)` is one of the modes it matches) on a touch context, and assert the bar's height, the title's top, the panel toggle's top and the shell's bottom padding.

## Composer paste recovery (`handlePaste` in `components/ChatInput.tsx`)

- Dictation tools (CosyVoice) write the transcript to the clipboard, post Cmd+V and restore the old clipboard soon after. When that write lands during the `paste` event, Chrome checks the clipboard again before inserting and drops its own insertion: `beforeinput insertFromPaste` with `data: null`, no `input` (#1513). The native paste stays in charge; `handlePaste` remembers the event's text and selection, `handleInput` clears that, and a `setTimeout(0)` inserts the text with `replaceTextareaRange()` only when no `input` came and the event was not prevented. Never take over every plain-text paste: Chrome's `execCommand("insertText")` takes seconds on a few thousand lines (4,000 lines: 13.6 s against 28 ms native).

## Terminal shell (`terminalShell()` in `lib/terminal-manager.ts`)
- A new terminal on Windows starts PowerShell as pi's `powershell` tool finds it, through the SDK's `getPowerShellConfig()`: PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and only without either `ComSpec` / `cmd.exe` (#1394). That is Windows Terminal's default too. The lookup is `where`, so a Store install's `WindowsApps` alias is what gets spawned; node-pty spawns it as it would the bare name. The tool's `-NoProfile -Command` arguments are not reused: the terminal is interactive. Elsewhere it is `$SHELL -l` (`/bin/sh` without `SHELL`).
- There is no shell setting and no `shell` field on `POST /api/terminal`: one default, and anyone who wants cmd or Git Bash types `cmd` / `bash` in the tab. A refreshed page's tabs reconnect to their own PTY (`createTerminal()` returns the record for a known id), so they keep the shell they started with; only new tabs pick it again.

## Terminal extra keys (`components/TerminalExtraKeys.tsx`, `lib/terminal-extra-keys.ts`)
- A touch device held in portrait gets Termux's two key rows under the terminal (`ESC / - HOME ↑ END PGUP`, `TAB CTRL ALT ← ↓ → PGDN`). Portrait comes from `screen.orientation` (then `window.orientation`), never from the viewport: the soft keyboard makes the viewport wider than tall, and the keys must stay while it is open. Left and right are Noto Sans Mono's `↓` and `↑` rotated 90deg: its latin subset has `↑`/`↓` but no `←`/`→`, which would fall back to a heavier system font.
- The keys are the panel's last grid row, so xterm's `ResizeObserver` refits above them instead of being covered. Buttons call `preventDefault()` on pointer and mouse down so the hidden xterm textarea keeps focus and the keyboard stays up.
- Keys go through `terminal.input(sequence, true)`, the same `onData` path (and the same connected / disableStdin checks) as typing. Arrows and Home/End follow xterm's application cursor mode; CTRL and ALT are one-shot and also modify the next character typed on the soft keyboard (`applyTerminalModifiers` in `onData`).

## Terminal theme (`lib/terminal-theme.ts`, `hooks/useTerminalTheme.ts`)
- The terminal header's sun/moon button switches the terminal alone between dark (the default) and light, apart from the app theme. The choice is per browser in `localStorage` (`pi-web:terminal-theme`), shared by every open terminal and synced across tabs by the `storage` event.
- A switch sets `terminal.options.theme` on the live xterm, never recreating it, so the shell and its SSE stream stay. The panel's chrome reads `--terminal-*` variables that `.terminal-panel[data-terminal-theme="light"]` overrides; `--terminal-bg` must match each xterm palette's `background`.

## Terminal font size (`terminalFontSize()` in `hooks/useChatAppearance.ts`)
- The terminal has no size setting of its own (#1277): it follows General's chat font size the way code blocks do, the same step from its own 13px at the 14px default (`terminalFontSize()`: chat − 1, so 11–23px). A slider move sets `terminal.options.fontSize` on the live xterm and refits through the panel's `fitAndResize`; the refit's `onResize` sends the new cols/rows to the PTY, the same path as a window resize.

## Sidebar breakpoint (`components/AppShell.tsx`)
- The mobile drawer starts closed on entering the mobile breakpoint. Desktop open state is remembered separately, seeded from the URL's initial `sidebarCollapsed` value and updated only by explicit desktop toggles. Returning to desktop restores that preference; mobile drawer toggles, backdrop clicks and toolbar actions must not replace it.

## Completion sound
- `hooks/useAudio.ts` stores the toggle in `localStorage` as `pi-sound-enabled` and reuses one `AudioContext`.
- Autoplay policy requires unlocking sound from a user gesture: `ChatInput` calls the unlock hook from interactive controls, and `ChatWindow` plays the tone from `onAgentEnd`.
- A running context keeps an audio output stream open even when silent (an Android `AudioMix` wake lock, #1157), so it runs only around a chime or an unlock: `AUDIO_IDLE_SUSPEND_MS` after the last `resume()` settled it is suspended, unless a newer one is still outstanding, and turning sound off suspends at once. An unlock resumes a suspended context from the send's gesture (about 1 s of output stream per send), which lets later chimes resume it without one (Chrome and Firefox check the page's sticky activation; WebKit lifts its gesture restriction for good once that context started in a gesture). It is never closed: a new context made outside a gesture would stay silent on Safari.
- Firefox for Android leaves the `resume()` of a suspended context pending while the phone is locked, so a run's chime never played there (device report on #1178). `ChatWindow` therefore holds the context running while its session's `agentRunning` is true (`holdAudio()`, released when the run ends or the window unmounts): the output stream stays open during a run, not between runs. Chimes for sessions in other workspaces come from the sidebar's running poll, which stops while the page is hidden, so they never needed a hold. A chime whose `resume()` took longer than `AUDIO_STALE_CHIME_MS` (3 s) is dropped instead of playing when the user is back, including one requested before the page's first gesture.
- A stopped run is not a finished one (pi 1.1's `agent_settled.aborted`, which pi's own status reporting reads as idle, not done): `onAgentEnd({ aborted })` plays no tone and the wrapper sends no completion push (`lastRunAborted`), so the server announces nothing for it. The wrapper's `prompt_done` carries `aborted: true` for it, since the client finishes a prompt it sent on `prompt_done`, not `agent_settled`. A new prompt clears it as the wrapper hands it to pi, not when pi accepts it: pi accepts a command that awaited a run of its own only after that run settled, and that run's Stop must still count.
- One completion, one alert (#1515). The server announces a finished run — the phone push to every subscription, and the Mac's own Notification Center row — a few hundred ms after the run settles. Both use the tag `pi-session-complete:<id>` with `renotify: true` (#701, so a later task re-alerts over an old notification still in the tray). The page used to raise a notification of its own beside them behind the same tag, which is what made one task alert twice; it raises nothing now (lib/task-completion-server.ts is the sender). Each push carries `data.shownAt`; the service worker shows every push (iOS revokes a subscription whose push shows nothing, #728) but with `renotify: false` when a same-tag notification is under `RECENT_NOTIFICATION_MS` (10 s) old. A push later than that still alerts twice.
- Only a run owes the completion push: the wrapper marks one at `agent_start` (`agentRunNeedsCompletion`), never when pi accepts a prompt. pi accepts an extension command it ran (and input an extension swallowed) as `handled` with no run, and reports a command that calls `pi.sendUserMessage()` handled before that run starts, so marking at acceptance pushed for every `command:` button and twice for a command that starts a run (#1345).
- A main session's run that ends while one of its subagents can still report back announces nothing: no push, no chime, no browser notification, no unread dot (#1434). Each background report starts a run in the parent (`notifyParent()`, `triggerTurn`), and the run after the last one is the end of the task. The one test is `hasUnsettledSubagentRun()` (`lib/subagent-runtime.ts`), the lease's `subagentsActive`: the wrapper skips the push, marks that run's `agent_settled` and `prompt_done` `subagentsActive: true` (`onAgentEnd({ subagentsActive })` then plays no chime), and `/api/agent/running` lists those sessions as `subagentsActiveSessionIds`, which the sidebar counts with the running ones, so a session completes when it leaves both, even if no poll saw its last run. A parent notification stops counting once the turn it triggers has started (pi sets the run active before its first await, and `sendCustomMessage()` resolves only after that turn settled), or else the turn's own end would still find it pending; one whose result the parent already collected with `get_subagent_result` does not count, since it is dropped without a turn. A report that cannot be delivered starts no run, so nothing is announced for it. A grandchild still running under a subagent that already reported does not hold the main session back: the main session never hears from it. A run leaves the run map in `finally` (`dropSubagentRun()`), and the queue reports `queued` before an item joins it, so a status write that throws (a full disk) cannot leave a run there that holds its parent's completion until a restart. Known limit: when an extension's async `agent_settled` handler outlasts the 200 ms parent poll, pi only queues the report's turn (`_deferredSettledActions`), the parent is not running yet, the pending entry goes when `sendCustomMessage()` returns, and that family is announced twice, as before this rule.

## The production page and its worker (`public/sw.js`, `public/offline.html`, `public/unavailable.html`, `public/offline-recovery.js`)

- **The worker has two builds, chosen by the `?v=` the page registers with** (`components/PwaRegistration.tsx`, `CACHE_VERSION` / `OFFLINE_MODE` in `public/sw.js`). Production (`?v=<app version>`) is the offline build: it precaches the fallback pages and the icons, answers `/_next/static/**` cache-first, and drops the old version's cache on activate. Development (`?v=dev`) is **push only**: it precaches nothing, handles no `fetch` at all, and its activate deletes every `pi-web-*` cache a production run left on the origin. Dev needs the worker for one reason: an iPhone added to the Home Screen can only subscribe to notifications through a registration, so a phone pointed at `npm run dev` over Tailscale had no way to turn "Notify this device" on (the switch reads "unsupported" with no registration, and it *was* the way to test the phone path). Dev must never read the cache: its chunk URLs are not content-hashed and the server is the thing being edited, so a cache-first asset feeds a previous build to the page and React reports the fresh HTML against the old bundle as a hydration mismatch. The desktop shell unregisters everything (`forgetWorkers`) — no offline requirement, and a worker survives an install in the webview's origin-scoped cache.
- **A navigation is answered by the server, and a page that says "offline" must be true.** `fetchWithTimeout` at 8 s used to answer a healthy server with the offline page, and the page's only advice is to reconnect — so a refresh of a loaded app on a working machine read "Pi Web is offline". `NAVIGATION_TIMEOUT_MS` is 15 s and the two fallbacks are separate: a refused connection (the server is not listening) is `offline.html` at once, a connection that is accepted and stays silent (the server is wedged, a request that starved) is `unavailable.html` when the budget expires. A cached HTML document is never an answer to a navigation.
- **Both pages heal themselves.** `public/offline-recovery.js` probes `/api/home` (the cheapest route, no auth on localhost) every 2 s and reloads when the app answers, backing off to 30 s, and keeps a `pi-web:offline-reload:<origin>` budget in `localStorage` of `MAX_RELOADS` (8) in `RELOAD_WINDOW_MS` (10 min) so a wedged server cannot make the browser flash forever. The budget must stay above the 2 reloads a real restart needs: one page consumes three, and a page that has spent its budget reloads on a real tap on "Try again". A fallback page has no app JS left to reconnect with — `public/sw.test.mjs` fails if either page loses the script, its auto-reload, the tap-to-reload, the budget, or the `/api/home` probe, and `public/offline-recovery.test.mjs` proves the self-heal in a DOM.
- **A browser gets about six open connections per host over HTTP/1.1, and this page holds long-lived ones** — the open session's `/api/agent/<id>/events`, the sidebar's running set, the scheduled stream, one file watcher, a terminal panel. A refresh whose document is 7th waits for a free socket and the worker reads that as offline. Two layers keep the pool: every page-wide stream goes through `openSharedEventStream[Handle]()` (`lib/scheduled-tasks/shared-stream.ts`) so the tabs of a browser elect one leader over a `pi-web:*` name and fan the frames out over a `BroadcastChannel` (the sidebar's running set: `lib/running-sessions-stream.ts`; the file watchers fan in per page over `/api/files?type=watch-all&paths=[{filePath,sessionId}]`, `lib/file-watch-channel.ts` + `lib/file-watch-stream.ts`, whose watched set is capped at 64 entries and filtered by the same roots, symlinks and `isCredentialPath()` rules as one file's `?type=watch`); and the production server is started with `--keepAliveTimeout 65000` (`bin/keep-alive.js`, `scripts/prod-server-flags.test.mjs`) because Next's 5 s default is shorter than a browser's keep-alive idle, so every focused-after-pause refresh rode a half-closed socket. A tab whose handlers must run per tab (the terminal panel's activity, audio) opens its own stream and says so in a comment.
- `e2e/offline-navigation.mjs` runs all of this against a real production server: saturates the pool and demands the "not answering" page in 15 s and its reload when the pool frees; kills the server and demands the offline page in under a second and its reload when it returns; refreshes across the keep-alive window; and checks that four open file tabs cost one file-watch connection, with the change of one of them delivered to its viewer.

## The image overlay's travel (`components/ImagePreview.tsx`)

A picture opened from the conversation is a full-screen `<dialog>`, and on a phone that
overlay had one control: the ×. A thumb had nothing to swipe, a trackpad's flick did
nothing, and a tap on the picture — what every photo app answers with "close" — did
nothing. The overlay now travels the pictures it belongs to: a finger's swipe
(40px, and horizontal-dominant, so a vertical drag is the page's), a trackpad's flick
(the horizontal wheel delta is summed, one page per burst, then a 260ms rest, because a
real flick sends dozens of momentum events), the arrow keys, and the ring in both
directions, so past the last picture of a turn is its first. A tap on the picture closes
it; a swipe's own trailing click is not a tap, and the mark that says so is cleared as
soon as the click is answered — a mark that outlives the swipe swallows the next tap,
which is exactly the bug the live probe caught.

The travel list is read from the DOM when the overlay opens, from the nearest
`[data-image-gallery]` container, and otherwise the rendered document (`.markdown-body`)
or the message (`.message-assistant`, `.message-user`): the conversation is what decides
the order of a turn's pictures, so no caller has to keep a list in step, and an image
inline in prose travels with the images of that document. The two direction plates are
`(pointer: coarse)` only — a mouse has the wheel and the arrows — and they are 44px, the
overlay's own control size, the close button's shape. The neighbour is fetched while the
current picture is looked at, so a swipe reveals a picture that is already there.

Check: `e2e/image-swipe.mjs` (the phone shape and the desktop shape, on Chromium and
WebKit: the count, the swipe, a mouse drag that is deliberately not a swipe, one flick
one page, the ring, the arrows, a tap that closes).
